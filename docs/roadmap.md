# 核心功能评估与迭代计划

> 基线：MallMini 当前版本（阶段 0–8 + 管理后台 UI 重构 + Android MVP）。
>
> 结论：主交易链路已闭环，但距离「可真实运营」仍缺 **售后/退款、库存流水、通知、后台权限与报表、履约增强** 五块 P0 能力。营销与增长能力放在 P1/P2，避免在交易可信之前过度建设。
>
> 真实微信支付与物流的接入步骤已分别拆到 [`wechat-integration.md`](./wechat-integration.md) 和 [`logistics-integration.md`](./logistics-integration.md)，本计划不把它们作为当前迭代的编码任务。
>
> **当前进度（R4 已完成）**：R1 售后/退款/库存/通知、R2 RBAC/审计/导出/自动确认/看板、R3 优惠券/运费模板/评价/收藏足迹、R4 搜索优化/客服工单/会员积分/首页运营位均已落地；真实支付/退款/物流、微信订阅消息、Android 售后/R3/R4 UI、电子发票仍未接入。

## 2. 评估方法

优先级按四个维度综合判断：

1. **资金与合规风险**：是否直接影响钱、库存、用户权益；
2. **交易闭环完整性**：缺失后是否必须人工兜底；
3. **用户可感知价值**：是否直接影响下单、履约、复购；
4. **实现成本与依赖**：是否需要外部资质、第三方服务或大改数据模型。

判定规则：

- **P0**：不做就无法真实运营，或会产生资金/库存风险；
- **P1**：影响转化、复购、运营效率，但可短期人工兜底；
- **P2**：增长或规模化能力，业务验证后再做。

## 3. P0：交易可信与可运营

### 3.1 售后与退款

**目标**：用户可对已支付订单发起仅退款/退货退款；管理员审核；退款结果可追踪；库存按规则回补。

**当前**：完全没有。`payment_status` 只有 `REFUNDED` 枚举，没有退款单、售后单、审核流。

**范围（首期）**：

- 仅退款（未发货/已发货但协商一致）；
- 退货退款（需填写退货物流）；
- 整单退款；部分退款先限制为按订单明细选择；
- 管理员审核通过/拒绝；
- 退款执行抽象：`RefundGateway`，首期可用「手工退款 + 模拟退款」；
- 退款成功后更新支付状态、写状态日志、按规则回补库存；
- 用户端售后列表/详情；管理后台售后列表/审核。

**数据模型**：

```text
after_sale_order
  id, after_sale_no, order_id, order_no, user_id,
  type(REFUND_ONLY/RETURN_REFUND), status,
  reason, description, evidence_json,
  refund_amount, return_company, return_tracking_no,
  applied_at, reviewed_at, reviewed_by, review_remark,
  returned_at, refunded_at, closed_at, created_at, updated_at

after_sale_item
  id, after_sale_id, order_item_id, quantity, refund_amount

refund_record
  id, refund_no, payment_id, order_no, channel,
  amount, reason, status, channel_refund_no,
  requested_at, success_at, failed_reason, created_at, updated_at
```

**状态机**：

```text
APPLIED
  -> REVIEWING
  -> APPROVED -> (RETURN_REFUND) WAIT_RETURN -> RETURNED -> REFUNDING -> REFUNDED
  -> (REFUND_ONLY) REFUNDING -> REFUNDED
  -> REJECTED
  -> CANCELLED
```

**接口**：

```text
POST /api/v1/me/orders/{orderNo}/after-sales
GET  /api/v1/me/after-sales
GET  /api/v1/me/after-sales/{afterSaleNo}
POST /api/v1/me/after-sales/{afterSaleNo}/cancel
POST /api/v1/me/after-sales/{afterSaleNo}/return-shipment

GET  /api/v1/admin/after-sales
GET  /api/v1/admin/after-sales/{afterSaleNo}
POST /api/v1/admin/after-sales/{afterSaleNo}/approve
POST /api/v1/admin/after-sales/{afterSaleNo}/reject
POST /api/v1/admin/after-sales/{afterSaleNo}/confirm-receipt
POST /api/v1/admin/after-sales/{afterSaleNo}/refund
```

**关键规则**：

- 退款金额不得超过「实付 − 已退款」；
- 同一订单同一明细的售后数量不得超过购买数量；
- 已取消/未支付订单不能发起售后；
- 退款执行必须幂等，`refund_no` 唯一；
- 退款成功前不得把订单标记为已退款；
- 仅退款默认不回补库存；退货退款在「确认收到退货」后回补；
- 所有状态变更写 `order_status_log`/售后日志，记录操作人；
- 客户端不能直接传目标状态。

**验收**：

- [ ] 未支付/已取消订单不能申请售后。
- [ ] 退款金额超出可退金额被拒绝。
- [ ] 重复审核/重复退款只生效一次。
- [ ] 退货退款在确认收货前不回补库存。
- [ ] 部分退款后订单支付状态与可退金额正确。
- [ ] 用户不能查看他人售后单。
- [ ] 退款失败可重试，不产生假成功。
- [ ] 管理后台审核有二次确认与操作日志。

**预估**：8–12 人日（不含真实支付渠道退款联调）。

**依赖**：可先做「手工退款/模拟退款」；真实微信退款在支付接入后补 `WechatRefundGateway`。

### 3.2 库存流水与预警

**目标**：每一次库存变化可追溯；支持手动调整、盘点和低库存提醒。

**当前**：只有下单条件扣减、取消回补；没有流水，无法解释库存差异。

**数据模型**：

```text
stock_log
  id, sku_id, product_id, change_type, quantity_delta,
  stock_before, stock_after, biz_type, biz_no,
  operator_type, operator_id, remark, created_at

stock_alert（可选，或直接查询阈值）
  id, sku_id, threshold, enabled, last_notified_at
```

`change_type`：

```text
ORDER_DEDUCT / ORDER_CANCEL_RESTORE / AFTER_SALE_RESTORE
MANUAL_ADJUST / PURCHASE_IN / STOCKTAKE / INIT
```

**接口**：

```text
GET  /api/v1/admin/stock/logs?skuId=&page=
POST /api/v1/admin/skus/{skuId}/stock/adjust
GET  /api/v1/admin/stock/alerts
PATCH /api/v1/admin/stock/alerts/{skuId}
```

**规则**：

- 调整库存必须写流水，禁止直接 `UPDATE stock`；
- 流水记录前后值，便于审计；
- 低库存阈值可配置，默认 10；
- 库存预警通过后台/通知触达；
- 并发扣减仍用条件更新，流水与扣减同事务；
- 取消回补/售后退货回补必须幂等，避免重复入库。

**验收**：

- [ ] 下单、取消、售后退货均产生正确流水。
- [ ] 手动调整后流水前后值连续。
- [ ] 并发扣减不出现负库存。
- [ ] 低库存 SKU 出现在预警列表。
- [ ] 重复取消不重复回补。

**预估**：4–6 人日。

### 3.3 通知中心

**目标**：支付成功、发货、退款、低库存等关键事件可触达用户/管理员；失败可重试。

**当前**：无任何通知。

**数据模型**：

```text
notification_log
  id, channel(MINIPROGRAM/SMS/IN_APP), template_code,
  biz_type, biz_no, user_id, payload_json,
  status(PENDING/SENT/FAILED), retry_count,
  sent_at, error_message, created_at, updated_at
```

**事件**：

- 支付成功；
- 订单发货；
- 退款申请/退款成功；
- 订单超时取消；
- 库存低于阈值（管理员）；
- 售后待审核（管理员）。

**实现要点**：

- 小程序订阅消息需先在微信公众平台配置模板，拿到模板 ID；
- 用户需在小程序内主动订阅，不能默认无限推送；
- 模板字段与订单数据映射；
- 外部发送放事务提交后（事件/Outbox），不在订单事务内发网络请求；
- 失败重试与告警，避免静默丢失；
- 日志不记录完整手机号、地址。

**验收**：

- [ ] 支付/发货/退款事件生成通知记录。
- [ ] 未授权订阅时不报错，记录跳过原因。
- [ ] 发送失败可重试，不重复轰炸。
- [ ] 通知内容不含敏感信息。
- [ ] 管理后台可查看发送失败记录。

**预估**：3–5 人日（不含模板审核等待）。

### 3.4 后台 RBAC、审计与导出

**目标**：多人运营时有权限边界；关键操作可追溯；订单/用户可导出。

**当前**：管理员只有一个 `ADMIN` 角色；有 `admin_operation_log` 写入，但没有查询页面；无导出；无改密。

**范围**：

- 角色：超级管理员、运营、客服、仓储（可按需）；
- 权限：菜单 + 接口双重校验；
- 管理员账号管理、重置密码、禁用；
- 操作日志查询与筛选；
- 订单/用户/库存导出 CSV/XLSX；
- 敏感字段按权限脱敏。

**数据模型**：

```text
admin_role (id, code, name, status, created_at, updated_at)
admin_permission (id, code, name, type(MENU/API), parent_id)
admin_role_permission (role_id, permission_id)
admin_user_role (admin_user_id, role_id)
```

若首期不想做完整 RBAC，可先做 `admin_user.role` 枚举 + 后端 `@PreAuthorize`，但数据模型应预留升级空间。

**接口**：

```text
GET/POST/PUT  /api/v1/admin/roles
GET           /api/v1/admin/admins
POST          /api/v1/admin/admins
PATCH         /api/v1/admin/admins/{id}/status
POST          /api/v1/admin/admins/{id}/reset-password
GET           /api/v1/admin/operation-logs
GET           /api/v1/admin/orders/export
GET           /api/v1/admin/users/export
```

**规则**：

- 前端隐藏按钮不等于权限控制，后端必须校验；
- 重置密码不返回明文，首次登录强制修改（可后续）；
- 管理员禁用后旧令牌立即失效（`token_version` 或每次查状态）；
- 导出异步生成文件，避免大表阻塞请求；
- 导出文件含手机号时必须脱敏或水印。

**验收**：

- [ ] 不同角色只能访问授权菜单/接口。
- [ ] 普通管理员不能创建超管。
- [ ] 操作日志可按管理员/动作/时间筛选。
- [ ] 导出字段与筛选条件一致。
- [ ] 禁用管理员旧令牌失效。

**预估**：5–8 人日。

### 3.5 订单履约增强

**目标**：减少人工跟单，覆盖常见履约动作。

**范围**：

- 自动确认收货：发货后 N 天（默认 7 天）自动完成；
- 发货前允许用户修改收货地址（需记录快照变更）；
- 订单备注：用户下单备注 + 管理员内部备注；
- 取消原因枚举化；
- 发票信息（抬头、税号、邮箱）与开票状态；
- 管理员订单备注/标记（如「加急」「已联系」）。

**验收**：

- [ ] 自动确认收货只执行一次，写 SYSTEM 日志。
- [ ] 已发货订单不能直接改地址；需走客服/售后流程。
- [ ] 备注在用户端/后台正确展示，不覆盖历史。
- [ ] 发票信息可保存、可导出，不伪造已开票。

**预估**：3–5 人日。

## 4. P1：转化与运营效率

### 4.1 优惠券与促销

**目标**：支持满减券、折扣券、无门槛券、新人券；服务端统一算价。

**数据模型**：

```text
coupon_template
  id, name, type(FIXED/DISCOUNT), value, min_amount,
  scope(ALL/CATEGORY/PRODUCT), scope_id,
  total_count, per_user_limit, valid_from, valid_to,
  status, created_at, updated_at

coupon
  id, template_id, user_id, status(UNUSED/USED/EXPIRED),
  order_no, used_at, valid_from, valid_to, created_at

order_discount
  id, order_no, coupon_id, type, amount, description
```

**规则**：

- 领取限领、有效期、库存；
- 下单锁定优惠券，取消/超时释放；
- 一单可用券规则明确（首期建议 1 张）；
- 优惠金额服务端计算，客户端只展示；
- 退款后优惠券是否退回需明确（首期建议整单退款退券，部分退款不退）；
- 与运费、活动价的叠加顺序写入业务文档。

**验收**：

- [ ] 过期/已用/不满足门槛的券不可用。
- [ ] 并发使用同一张券只成功一次。
- [ ] 取消订单释放券，且只释放一次。
- [ ] 篡改客户端金额不影响服务端结果。
- [ ] 退款后的券状态符合规则。

**预估**：8–12 人日。

### 4.2 商品评价

**目标**：已完成订单可评价；支持评分、文字、图片、匿名；后台审核/回复。

**数据模型**：

```text
product_review
  id, order_no, order_item_id, product_id, sku_id, user_id,
  rating, content, images_json, anonymous,
  status(PENDING/APPROVED/REJECTED), reply,
  created_at, updated_at
```

**规则**：

- 仅已完成订单可评价；
- 同一订单明细只能评价一次；
- 评价审核后展示；
- 商品评分由已审核评价聚合，可缓存；
- 不伪造评价/销量。

**预估**：4–6 人日。

---

### 4.3 收藏与浏览足迹

**目标**：用户收藏商品、查看浏览记录，提升复购。

**数据模型**：

```text
favorite (id, user_id, product_id, created_at, unique(user_id, product_id))
browse_history (id, user_id, product_id, viewed_at, index(user_id, viewed_at))
```

**规则**：

- 收藏状态实时同步；
- 浏览记录保留最近 N 条，可清空；
- 下架商品展示「已下架」；
- 游客可不记录，登录后合并策略明确。

**预估**：2–3 人日。

### 4.4 搜索优化

**目标**：商品量增长后仍有可用的搜索与筛选。

**方案**：

- 首期：MySQL `FULLTEXT` + `ngram` 分词，标题/副标题/描述；
- 热搜词/搜索日志表；
- 筛选：分类、价格区间、销量、上新；
- 排序：综合、销量、价格、新品；
- 商品量超过 10 万再评估 Elasticsearch/OpenSearch。

**验收**：

- [ ] 中文关键词可命中。
- [ ] 无结果有明确空态与推荐。

- [ ] 搜索接口有分页与最大页限制。
- [ ] 热搜词不展示违规内容。

**预估**：4–6 人日。

### 4.5 运费模板

**目标**：按地区、重量/件数计算运费，支持包邮规则。

**数据模型**：

```text
shipping_template
  id, name, free_threshold, status, created_at, updated_at
shipping_template_rule
  id, template_id, region_codes, first_unit, first_fee,
  additional_unit, additional_fee, free, sort_order
product_shipping
  product_id, template_id
```

**规则**：

- 商品未绑定模板时使用全局默认；
- 地区匹配优先级明确（精确 > 省级 > 全国）；
- 结算预览与下单使用同一算价服务；
- 运费模板变更不影响历史订单；
- 首期可不做偏远地区加价，但数据模型预留。

**预估**：4–6 人日。

### 4.6 数据报表与经营看板

**目标**：能回答「卖了多少、退了多少、哪里在漏」。

**指标口径**（必须写进文档）：

- GMV：已支付订单商品金额（是否含运费/退款需明确）；
- 实收：支付金额 − 已退款；
- 订单数：支付订单数/有效订单数；
- 客单价：实收 / 支付订单数；
- 退款率：退款金额 / 支付金额；
- 转化率：下单用户 / 访问用户（需要埋点）；
- 库存周转：出库数量 / 平均库存（需要库存流水）。

**范围**：

- 时间范围筛选；
- 趋势图、分类销售、Top 商品；
- 待处理订单、退款待审、低库存；
- 导出；
- 明确空态与演示数据标识。

**预估**：5–8 人日（依赖库存/退款数据）。

### 4.7 客服入口

**目标**：用户能找到人，而不是只有假按钮。

**方案**：

- 首期：客服电话/企业微信二维码/邮箱，明确服务时间；
- 二期：在线客服（第三方 SDK）或工单；
- 订单详情带订单号跳转；
- 不伪造「在线客服」状态。

**预估**：3–5 人日（首期可 1 人日）。

## 6. 迭代计划

> 以 1 名全栈开发估算，含自测与文档；不含真实支付/物流联调等待时间。

### R0：清理与准备（1 人日）— ✅ 已完成

- 修复小程序假入口；
- 统一状态文案；
- 补充售后/退款数据模型设计评审；
- 确认退款首期是「手工退款」还是「等待真实支付」。

### R1：售后与资金安全（10–15 人日）— ✅ 已完成

- 售后单/退款单表与状态机；
- 用户申请、取消、退货物流；
- 管理员审核、确认收货、退款；
- 退款抽象 + 手工/模拟退款；
- 库存流水（与售后退货回补联动）；
- 通知：售后审核、退款结果；
- 测试：金额、幂等、越权、并发、库存回补。

**交付标准**：已支付订单可以完成一次完整的仅退款/退货退款；库存与支付状态一致；后台可审计。

**实际交付**：`after_sale_order/item/log`、`refund_record`、`stock_log`、`notification_log`；用户申请/取消/退货物流；管理员审核/拒绝/确认收货/退款；模拟与线下手工退款；库存流水与预警；站内通知；小程序与管理后台页面。真实微信退款与订阅消息不在本次范围。

### R2：运营底座（8–12 人日）— ✅ 已完成

- RBAC/管理员管理/改密/禁用；
- 操作日志页面；
- 订单/用户/库存导出；
- 自动确认收货；
- 订单备注、发票信息、地址修改规则；
- 数据看板升级（GMV、退款率、客单价、待办）。

**交付标准**：多人可分角色运营；订单可自动完成；关键经营指标可查。

**实际交付**：角色权限矩阵与接口校验、管理员管理/改密/禁用、操作日志页面、订单/用户/库存 CSV 导出、超时自动确认收货、订单后台备注、发票信息、待发货改地址、看板升级（净收入/退款率/客单价/趋势/售后待处理/低库存）。真实电子发票与大数据量异步导出不在本次范围。

### R3：转化能力（12–18 人日）— ✅ 已完成

- 优惠券/促销算价；
- 运费模板；
- 商品评价；
- 收藏/浏览足迹；
- 通知模板补齐（支付/发货/退款）。

**交付标准**：营销活动可配置、算价可信、评价可展示；退款/取消时优惠券与库存状态正确。

**实际交付**：优惠券模板/领取/结算算价/下单锁定/取消释放、运费模板（省份/首件续件/包邮）与商品绑定、商品评价（待审核/通过/拒绝/回复、评分聚合）、收藏与浏览足迹。真实电子发票、评价图片、复杂促销叠加不在本次范围。

### R4：体验与增长（8–12 人日）— ✅ 已完成

- 搜索优化（全文/筛选/热搜）；
- 客服入口/工单；
- 会员积分（如业务确认需要）；
- 首页运营位扩展。

**交付标准**：商品量增长后搜索可用；用户能找到客服；复购激励可配置。

**实际交付**：搜索热词与 ngram 全文索引、销量排序、首页新品/热销/快捷入口、会员积分（完成奖励/整单退款扣回/等级）、客服工单（提交/回复/关闭）与后台积分调整。积分抵现、工单附件/推送、ES 搜索不在本次范围。

### R5：真实外部能力与上线（按需）

- 按 [`wechat-integration.md`](./wechat-integration.md) 接真实微信支付/退款/对账；
- 按 [`logistics-integration.md`](./logistics-integration.md) 接物流轨迹/订阅/自动确认；
- Redis/对象存储/监控/CI/CD；

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 退款规则复杂，边界多 | 资金错误、客诉 | 先做整单/按明细的有限场景；状态机与幂等测试先行 |
| 真实支付未接入 | 退款只能手工 | 退款抽象与手工退款先上线，真实网关后补 |
| 库存流水改造影响下单 | 超卖/少卖 | 流水与扣减同事务；灰度前压测并发 |
| 订阅消息模板审核 | 通知延期 | 提前申请模板；失败降级站内信/短信 |
| 报表口径不一致 | 经营误判 | 指标口径写入文档；与财务对账 |
| 权限模型过度设计 | 拖慢交付 | 首期角色+接口权限，预留表结构 |
| 物流供应商频控/计费 | 成本与稳定性 | 缓存、限流、订阅优先、灰度 |
| 范围蔓延 | 迭代失控 | P2 明确不做；每个迭代只承诺 DoD 内范围 |
